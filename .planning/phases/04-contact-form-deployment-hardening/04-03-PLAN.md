<objective>
Wire the Footer's static 3-field contact form (Phase 3's markup-only baseline, D-07) into a real submission flow: `preventDefault()` (D-12 fix), a honeypot spam check (D-10), a real `fetch('/api/contact', ...)` call, and the three new UI states — submitting, success, error — specified in 04-UI-SPEC.md.

Purpose: CONT-01 (delivery) and CONT-02 (feedback) are this phase's job on top of Phase 3's inert form. Today the form has `type="submit"` with no `onSubmit`, so a real click triggers a native full-page GET reload (03-REVIEW.md should-fix, D-12). This plan fixes that and adds every state 04-UI-SPEC.md specifies, all sourced from `footerContent` per the project's established content-as-data-module pattern. Per CONTEXT.md D-09, feedback is inline (not a toast/banner): success replaces the form fields in place with a confirmation message, and error shows an inline message above the form with the user's entered field values preserved — no data loss on failure.

Flagged assumption (04-UI-SPEC.md UI Considerations, unresolved item): native browser `required`-field validation-bubble styling (the default outline/tooltip a browser shows on an empty required field) is accepted as-is for v1 — no custom validation-error treatment is built beyond the browser default, since CONTEXT.md does not specify one distinct from the server-side error banner.

Output: Updated `src/content/footer.ts` (5 new copy fields), `src/components/home/Footer.tsx` (real submit handler + 3-state conditional render), `src/components/home/Footer.test.tsx` (extended coverage).
</objective>
