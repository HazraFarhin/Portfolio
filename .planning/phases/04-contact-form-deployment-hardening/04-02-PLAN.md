<objective>
Create the Vercel serverless function that delivers the contact form via Resend (CONT-01), and the `vercel.json` SPA rewrite that makes case-study deep links survive a direct load/refresh (DEPL-02) — the two pieces of net-new backend/deploy infrastructure this phase introduces.

Purpose: Neither exists in the repo today (no `/api` directory, no `vercel.json`). 04-RESEARCH.md's Architecture Patterns give the exact, officially-documented shapes for both: a dependency-free Web Standard `fetch` export for the function (Pattern 1), explicit `{ data, error }` → JSON status-code forwarding for the Resend call (Pattern 2), and a single-rule catch-all rewrite for SPA routing (Pattern 3). Deploying to Vercel rather than Netlify (D-04) is why this function lives at `/api/contact.ts` and why `vercel.json` is the config file created — Vercel's first-party Vite detection and `/api/*.ts` serverless-function convention match this repo's existing TypeScript setup directly. Sending from Resend's default `onboarding@resend.dev` address with `to` hardcoded to `hazrafarhinwork@gmail.com` (D-02) is why the recipient is never accepted as user input in this function.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Browser (untrusted public client) → api/contact.ts (Vercel Function, server-side) | Any client can POST to `/api/contact` with arbitrary content; the function is the first trust boundary that validates it |
| api/contact.ts → Resend API (external service) | `RESEND_API_KEY` custody boundary — the key must never cross back into the client bundle |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-04-01 | Information Disclosure | RESEND_API_KEY custody in api/contact.ts | high | mitigate | Read only via `process.env.RESEND_API_KEY` inside `api/contact.ts` (server-side Vercel Function code, never bundled by Vite); never prefix the env var `VITE_` anywhere in this codebase — a `VITE_`-prefixed var is inlined into the client JS bundle at build time |
| T-04-03 | Tampering | `subject` string interpolation of the `email` field | medium | mitigate | Reject any `email` value containing `\r`/`\n` before calling Resend (Task 1) — Resend's `emails.send` takes `subject`/`text` as discrete JSON fields (not raw SMTP header text), which structurally prevents classic header injection, but newline-stripping is still applied defensively since `email` is interpolated into the subject string |
| T-04-04 | Tampering | Direct POST to /api/contact bypassing all client-side checks (e.g. curl) | medium | mitigate | Server-side re-validation of required fields + email-shape regex inside `api/contact.ts` (Task 1) — the client's `required` HTML attributes provide UX only, never trusted as the sole validation layer |
| T-04-05 | Tampering / Information Disclosure | Resend `to` field | low | mitigate | `to` hardcoded to the literal `'hazrafarhinwork@gmail.com'` inside `api/contact.ts`, never accepted as user input — Resend's own unverified-domain restriction (D-02) is a secondary backstop, not the primary control |

</threat_model>
