# Phase 4 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** Phase 4 is primarily backend/infra (Resend serverless function, Vercel deployment, robots.txt/sitemap). Its ONE frontend surface is the contact form in `src/components/home/Footer.tsx`, which gains real inline success/error states on submit (D-09, D-10, D-11, D-12) and loses its "see more" deferred-slug links in `src/components/home/SelectedWork.tsx` (D-07, D-08). This contract covers both: the new interaction states in full detail, and the SelectedWork simplification as a removal (no new visual language needed there).

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-built `src/components/ui/` primitives (`Button`, `Card`, `Typography`) established in Phase 1 and reused through Phases 1–3 |
| Icon library | `lucide-react` 1.26.0 (already a dependency, already used in `ImagePlaceholder.tsx`) — this phase's new icons: `CheckCircle2` (success) and `AlertCircle` (error) |
| Font | Inter (`--font-sans`, already loaded) |

**Why "none" and not shadcn:** `components.json` does not exist and this project deliberately never adopted shadcn — Phase 1's success criteria explicitly established a shared custom `components/ui/` primitive set precisely so later phases reuse it rather than introducing a second component system. Introducing shadcn now, for one form's state additions, would fork the design system mid-project. This UI-SPEC's job is to extend the existing primitives (`Button`, `Typography`'s `Body`/`Label`), not replace them.

## Spacing Scale

Declared values (project's existing `@theme` tokens, `src/index.css` — reuse as-is, do not introduce new spacing values):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon-to-text gaps (e.g. `CheckCircle2`/`AlertCircle` next to headline text) |
| sm | 8px | Compact stacks — form field label-to-input gap (existing `gap-xs` is 4px; field internal padding is `py-sm`) |
| md | 16px | Default field/element spacing — form `gap-md`, input `px-md`/`py-md`, gap between error banner and form |
| lg | 24px | Success/error block internal padding, gap between form-brief intro and form |
| xl | 32px | Layout gaps between Brief block and Footer block |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing |

Exceptions: The honeypot field (D-10) is NOT part of the visible spacing rhythm — it must be visually and programmatically hidden without `display:none` (which some spam bots and autofill heuristics skip). Use the standard accessible-hiding technique: `absolute` positioning, `w-px h-px`, `overflow-hidden`, `opacity-0`, plus `aria-hidden="true"` and `tabIndex={-1}` on the input, and `autoComplete="off"` so password managers/autofill never populate it. It occupies no space in the visible layout and must never receive a spacing token.

## Interaction & Motion Contract

The project's motion system (`useScrollReveal`, GSAP-driven) is reserved for scroll-triggered entrance reveals of whole sections — it is NOT the right tool for a discrete state swap inside an already-visible form. Use plain CSS transitions instead, which are automatically reduced-motion-safe via the existing global override in `src/index.css` (the `@media (prefers-reduced-motion: reduce)` block already zeroes all `transition-duration` site-wide — no per-component reduced-motion branching needed here, consistent with QUAL-02's centralized approach).

- **Idle → Submitting:** `Button` label swaps text ("Send the Brief →" → "Sending…"), `disabled` attribute set on the button, form fields set `aria-busy="true"` on the `<form>`. No layout shift — button retains its size.
- **Submitting → Success (D-09):** the entire `<form>` element is replaced in place (conditional render, same container, same `mt-lg` position relative to the brief intro copy) by the success block. Cross-fade via `transition-opacity duration-200 ease-out` on the incoming block (fade in from `opacity-0`); no vertical translate/slide — this is a content swap, not a scroll reveal, so it should read as instant-but-smooth, not as a repeat of the section's own entrance animation.
- **Submitting → Error (D-09):** an error banner is inserted ABOVE the form (between the brief intro `Body` copy and the `<form>`), and the form itself remains mounted with all field values intact (uncontrolled inputs retain their DOM value across a failed `fetch` automatically — no controlled-component state resync needed, no data loss). Same `transition-opacity duration-200 ease-out` fade-in on the error banner only; the form does not animate.
- **Honeypot-triggered silent reject (D-10):** renders the IDENTICAL success block as a genuine submission — same copy, same transition, no network call made. This is deliberate: showing a different outcome (or no outcome) for the honeypot path would let a bot detect the mechanism via response variance. A real user never triggers this path since the field is invisible to them.
- **Retry from error state:** the error banner clears (fades out, same 200ms) as soon as the user resubmits and a new request starts (return to Submitting state); it does not persist stacked with a second attempt.
