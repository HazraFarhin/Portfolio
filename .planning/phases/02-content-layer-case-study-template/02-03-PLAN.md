## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Raw `.md` file text -> parsed/validated in-memory object | Content-integrity boundary: first-party-authored files today (D-12), but the validation layer is the only gate between "whatever is in the file" and "what the app trusts as typed data" |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|------------------|
| T-02-03 | Tampering | `external_link` frontmatter field reaching an `<a href>` | medium | mitigate | Zod's bare `.url()` accepts any URL-spec-valid scheme (including `javascript:`); this plan adds an explicit `.refine()` restricting to `http://`/`https://` only, closing that gap before any component renders the value into an anchor |
| T-02-04 | Tampering | Unrecognized/extra frontmatter keys silently accepted | low | mitigate | `CaseStudyFrontmatterSchema` uses `.strict()` (not the Zod default of silently stripping unknown keys), so any malformed or unexpected key fails validation loudly at parse time instead of passing through ungoverned to rendering |
| T-02-05 | Tampering (data integrity) | Broken/malformed frontmatter silently reaching production | low | accept | `parseCaseStudyFile()` throws immediately and synchronously on invalid frontmatter (fail-fast); Plan 02-08's loader is responsible for catching this per-file so one bad file doesn't take down all 6 (see Plan 02-08's threat model) |
